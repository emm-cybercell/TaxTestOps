> 源码路径：`src/tax_service/platform/` & `tests/`  
> 编写日期：2026-11-02

## 1. 架构全景

TaxTestOps 采用**双应用分离、同仓演进**的工程架构：
1. **被测服务（SUT - Subject Under Test）**：提供个人所得税计算、专项附加扣除拆解、申报记录持久化与幂等校验等核心业务 API。
2. **测试平台（TestOps Platform）**：提供用例数据化管理、批量异步调度引擎、WebSocket 实时执行日志回传、历史度量趋势看板与 AI 智能赋能套件。

## 2. 测试分层设计与实施

自动化测试体系遵循经典的金字塔分层模型，每一层分工边界清晰，严禁职责跨层倒挂：

| 分层 | 目录位置 | 核心工具链 | 覆盖目标与关键职责 | 执行速度 |
|---|---|---|---|---|
| **单元测试 (Unit)** | `tests/unit/` | pytest, coverage | 控制流分支覆盖、V(G)=18 独立路径验证、AST 语法树圈复杂度机器校验、政策数据契约 | 毫秒级 (~0.3s) |
| **接口测试 (API)** | `tests/api/` | httpx, pydantic, pyjwt | HTTP 状态码契约、参数格式校验、JWT 鉴权生命周期、跨字段互斥校验、幂等重放一致性 | 秒级 (~5s) |
| **集成测试 (Integration)** | `tests/integration/` | SQLite, respx, threading | 数据库唯一约束并发写入、外键级联删除、缓存 TTL 失效与击穿降级、固定窗口限流 | 秒级 (~12s) |
| **契约测试 (Contract)** | `tests/contract/` | schemathesis, hypothesis | OpenAPI 3.0 规范反向验证、JSON Schema 自动递归展开、基于属性的模糊测试（Fuzzing 5xx 拦截） | 秒级 (~7s) |
| **UI 自动化 (UI)** | `tests/ui/` | Playwright (Chromium) | Page Object 模型、用户登录态维持、表单交互端到端走查、网络事件重试等待 | 十秒级 (~22s) |
| **性能测试 (Perf)** | `tests/perf/` | Locust, ThreadPool | 多用户高并发测算、读写分离延迟、P50/P95/P99 延迟基线守卫、并发落库零丢失校验 | 十秒级 (~14s) |
| **平台层自测 (Platform)** | `tests/platform/` | TestClient, WebSockets | 测试平台自身用例 CRUD、批次状态流转、调度器中断机制、WebSocket 实时订阅广播 | 秒级 (~30s) |

## 3. 关键架构设计与工程亮点

### 3.1 双模式对照引擎（Legacy vs Standard）
为了彻底证明测试集本身的“有效性”，系统内置了双计算引擎：
- **`legacy`（缺陷保留版）**：忠实复刻高校实验原实现中的 30 行纯 Java 逻辑，保留阶梯税率第 3 级起速算扣除数少计 1300 元、房贷租金双扣、除零隐患等 9 项缺陷。
- **`standard`（国标规范版）**：按国标月度综合所得超额累进税率表、表驱动算法以及参数统一校验层重新实现。

通过环境变量 `TAX_CALCULATOR_IMPL` 可无缝切换运行：
- 在 `legacy` 模式下，针对已知缺陷的需求符合性断言被标记为 `xfail(strict=True)`（32 条 xfail，0 意外失败）；
- 在 `standard` 模式下，全部需求断言**100% 真实转绿**（630+ 用例无任何 xfail 或 failure）。
> **面试阐述亮点**：一个只会在 bug 上标红的框架无法自证有效；双模式切换证明了测试用例不仅能拦截缺陷，更能在缺陷修复后成为精确的质量守护网。

### 3.2 幂等重放数据一致性保护
在单次测算接口 `POST /api/v1/tax/calculate` 中，客户端可携带 `idempotency_key`。
- **先查后写 + 数据库唯一约束兜底**：利用 `(user_id, idempotency_key)` 联合唯一索引拦截并发写穿透；
- **重放数据严格溯源**：发生幂等命中时，服务端**严禁就地重新计算**，而是使用首次落库记录重组返回报文。杜绝了调用方在不同时刻拿到“相同 ID 但不同金额”的致命账目不一致问题。

### 3.3 平台用例数据化与批次执行引擎
在 `tax_service.platform` 中，用例被建模为数据库实体（`TestCase`），断言定义以 JSON 数据（`path`、`op`、`value`）存储。
- **安全路径解析器**：自研 `resolve_path` 支持点号与数组下标混合解析（如 `deductions.0.amount`），严格收敛字段访问边界；
- **独立故障隔离**：单条用例执行异常被包裹为 `CaseOutcome(status=ERROR)`，整批执行永不中断，保障持续集成反馈的完整性；
- **Flaky 用例识别器**：记录重试尝试次数（`attempts`），自动将“重试后通过”的用例归档为疑似 Flaky 用例，为测试套件稳定性治理提供数据抓手。

### 3.4 WebSocket 实时事件流与调度系统
- 采用 `RunEventBroker` 维护按执行批次隔离的异步消息队列；
- 执行发生在独立的工作线程池，利用 `loop.call_soon_threadsafe` 将事件投递至主事件循环的 WebSocket 连接；
- 队列设置丢弃保护策略（丢弃最旧事件），杜绝慢客户端背压拖垮执行引擎。

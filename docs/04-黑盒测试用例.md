# 04 · 黑盒测试用例（需求驱动）

> 期望值来源：需求文档中的政策数值 + 独立实现的测试预言 `TaxOracle`
> 用例实现：`tests/unit/test_requirements.py`、`tests/unit/test_oracle.py`、`tests/unit/test_policy.py`
> 执行结果：**21 passed / 14 xfailed**（xfail = 已确认缺陷，见 [05](05-缺陷分析报告.md)）

---

## 1. 设计方法

黑盒用例**完全不参考被测代码的内部结构**，只依据需求规格设计。四种方法组合使用：

| 方法 | 适用场景 | 本文档位置 |
|---|---|---|
| 需求样例复现 | 需求文档自带算例，作为回归基线 | 第 2 节 |
| 等价类划分 | 输入域可划分为若干等价区间 | 第 3 节 |
| 边界值分析 | 缺陷高发于区间边界 | 第 4 节 |
| 判定表 | 多个输入条件存在业务互斥约束 | 第 5 节 |
| 错误推测 | 基于经验的补充用例 | 第 6 节 |

### 期望值从哪来：测试预言问题

黑盒测试的核心难点是「期望值谁说了算」。只用被测代码自己的输出做断言，无法区分「算对了」和「本来就这样」。本项目构建了**来源独立**的测试预言：

```
需求文档 ──┬─→ 政策数值（扣除标准、税率表）──→ 测试期望值
           │
           └─→ 独立实现 TaxOracle（表驱动）──→ 测试期望值
                          ↑
                   与 SUT 实现方式不同
                （SUT：硬编码 if 分支 / Oracle：税率表遍历）

两者不一致 ──→ 判定为 SUT 缺陷（而非「两边都错」）
```

`TaxOracle` 自身也受测试保护（`tests/unit/test_oracle.py`，43 条用例）——否则 Oracle 出错会把错误当成需求。详见该文件头部说明。

## 2. 需求样例复现

需求文档给出的两个算例，直接作为回归基线：

| 编号 | 来源 | 输入 | 需求期望 | 实际 | 结论 |
|---|---|---|---|---|---|
| BB-01 | 需求原文 | 月收入 10000，三险一金 2000，无专项附加扣除<br>→ `Person()`, `salary = 8000` | (10000−5000−2000)×3% = **90** | 90 | 通过 |
| BB-02 | 需求原文 | 小李：月收入 10000，三险一金 2000，租金 1500，一子女，与姐姐分摊赡养<br>→ `Person(children_num=1, is_rent_house=1, supporting_elderly=True, sibling_num=1)`, `salary = 8000` | (10000−5000−2000−1500−1000−1000)×3% = **0** | 0 | 通过 |

> 说明：`cal` 的 `salary` 参数约定为「已扣除三险一金」，故传入 8000 元。
>
> 两个样例都通过，说明**该实现的缺陷不在常见工资区间**——这也解释了为什么它能通过课程验收。

## 3. 等价类划分

### 3.1 输入域等价类表

| 输入变量 | 有效等价类 | 无效等价类 | 实现是否校验 |
|---|---|---|---|
| `person` | 非空对象 | 为 `null` | ✓ 抛 `TypeError` |
| `salary` | ≥ 0 的整数 | < 0 | ✓ 抛 `ValueError` |
| `children_num` | ≥ 0 的整数 | < 0 | ✗ **未校验（D5）** |
| `is_keep_stu` | `{0, 1, 2}` | 其他整数 | ✗ **静默忽略（D5）** |
| `house_loans` | `true` / `false` | — | — |
| `is_rent_house` | `{0, 1, 2, 3}` | 其他整数 | ✗ **静默忽略（D5）** |
| `supporting_elderly` | `true` / `false` | — | — |
| `sibling_num` | ≥ 0 的整数 | = −1（除数为 0） | ✗ **崩溃（D3）** |
| `house_loans` × `is_rent_house` | 至多一项为真 | 两项同时为真 | ✗ **双扣（D2）** |

### 4.2 边界连续性检查

阶梯税率函数在分界点处**本应连续**（收入多 1 元，税额增加 `1 × 边际税率`）。检查第 2/3 级分界点：

| 应纳税所得额 | 需求实现 | 当前实现 |
|---|---|---|
| 11999 | 989 | 989 |
| 12000 | 990（+1） | **2290（+1301）** |

**当前实现在此处出现 1301 元的跳变**——这是黑盒边界值测试能直接捕获 D1 的原因，也是该类缺陷最直观的表征。

### 4.3 边界值方法的有效性

| 测试方法 | 是否发现 D1 | 原因 |
|---|---|---|
| 等价类划分（取代表值） | 可能漏 | 若代表值恰好取在第 2 级，则完全正常 |
| **边界值分析** | **必然发现** | 缺陷恰好在分界点处表现为跳变 |
| 需求样例复现 | 漏 | 需求样例工资较低，落在第 1/2 级 |

> 这个对比说明：**边界值分析不是等价类划分的补充，而是独立且更有效的缺陷发现手段**。

## 5. 判定表：住房贷款利息 × 住房租金

### 5.1 规则表

需求规定：**住房贷款利息与住房租金不可同时享受**（二者只能选其一）。

| 规则 | 住房贷款利息 | 住房租金 | 需求规定动作 | 实现动作 |
|---|---|---|---|---|
| R1 | 否 | 无（档次 0） | 不扣除 | 不扣除 ✓ |
| R2 | **是** | 无（档次 0） | 扣除 1000 元 | 扣除 1000 元 ✓ |
| R3 | 否 | 档次 1 / 2 / 3 | 按档次扣除 1500 / 1100 / 800 元 | 按档次扣除 ✓ |
| R4 | **是** | **档次 1 / 2 / 3** | **拒绝非法输入** | **两项同时扣除 2500 元** ✗ |

### 5.2 判定表用例表

扣除额用**相对口径**验证（与无扣除的基准比较），从而不受缺陷 D1 常量偏移干扰：

| 编号 | 规则 | 输入（`salary = 20000`） | 预期税额降幅 | 实际降幅 | 结论 |
|---|---|---|---|---|---|
| BB-11 | R1 | `Person()` | 0 | 0 | 通过 |
| BB-12 | R2 | `Person(house_loans=True)` | 1000 × 20% = **200** | 200 | 通过 |
| BB-13 | R3 | `Person(is_rent_house=1)` | 1500 × 20% = **300** | 300 | 通过 |
| BB-14 | R3 | `Person(is_rent_house=2)` | 1100 × 20% = **220** | 220 | 通过 |
| BB-15 | R3 | `Person(is_rent_house=3)` | 800 × 20% = **160** | 160 | 通过 |
| BB-16 | **R4** | `Person(house_loans=True, is_rent_house=1)` | **拒绝非法输入** | **双扣 2500，税额降 500** | **失败（D2）** |

### 5.3 R4 的缺陷验证

```
输入：Person(house_loans=True, is_rent_house=1), salary = 20000
res = 20000 − 5000 = 15000
    − 1000（住房贷款利息）      ← 不应发生
    − 1500（住房租金）          ← 不应发生
    = 12500

当前实现税额：2290 + (12500 − 12000) × 0.2 = 2390
若只扣租金：  2290 + (13500 − 12000) × 0.2 = 2590
若只扣房贷：  2290 + (14000 − 12000) × 0.2 = 2690
无任何扣除：  2290 + (15000 − 12000) × 0.2 = 2890

2390 < 2590 < 2690 < 2890 → 两笔扣除均生效，确认为缺陷
```

## 6. 错误推测与需求符合性核对

| 编号 | 推测依据 | 用例 | 预期 | 实际 | 结论 |
|---|---|---|---|---|---|
| BB-17 | 子女数应为线性影响 | 0 / 1 / 2 名子女的税额差 | 每多一名子女税额降 200 元（1000 × 20%） | 降 200 元 | 通过 |
| BB-18 | 继续教育月度标准 | `Person(is_keep_stu=1)` | 降 400 × 20% = 80 元 | 80 元 | 通过 |
| BB-19 | **继续教育年度标准** | `Person(is_keep_stu=2)` | 3600 元为年度定额，不应逐月扣除 | **逐月扣 3600，全年多扣 39600 元** | **失败（D4）** |
| BB-20 | 赡养老人分摊 | 独生子女 vs 1 名兄弟姐妹 | 独生子女扣 2000，分摊后扣 1000 | 差 1000 × 20% = 200 元 | 通过 |
| BB-21 | 缺陷影响范围界定 | 遍历 `res ∈ [0, 12000)` 每 250 元 | 与需求完全一致 | 完全一致 | 通过 |

### BB-19 的详细分析

需求原文：

> 继续教育: 在学历（学位）教育期间每月 400 元，**在取得相关证书的当年，按照 3600 元定额扣除**

「当年按 3600 元定额扣除」是**年度**语义，而 `cal` 是**月度**计算函数。当前实现直接把 3600 元从当月应纳税所得额中扣除：

```
输入：Person(is_keep_stu=2), salary = 20000
res = 15000 − 3600 = 11400 → 税额 930 元

按年度定额处理（Oracle 口径）：res = 15000 → 税额 1590 元

全年影响：3600 × 12 = 43200 元，是政策值 3600 元的 12 倍
```

这属于**需求语义与函数语义错配**——既是实现缺陷，也暴露了需求描述不够精确（未说明年度项在月度函数中如何处理）。

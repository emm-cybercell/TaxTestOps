# 03 · 白盒测试用例（独立路径覆盖）

> 前置：[01-控制流图与圈复杂度](01-控制流图与圈复杂度.md)、[02-独立路径分析](02-独立路径分析.md)
> 用例实现：`tests/unit/test_path_coverage.py`
> 执行结果：**19 passed**（18 条独立路径 + 1 条元测试）

## 1. 设计方法

白盒用例按 [02](02-独立路径分析.md) 推导出的 **18 条独立路径**逐条设计，每条路径对应
一个用例，目标是：

1. 让每条独立路径**实际被执行到**；
2. 断言该路径的**实际输出**，把当前行为固定下来（特征化断言）。

用例编号与路径编号一一对应（`WB-01` ↔ `P1`），便于在流图上回溯。

### 输入数据的选取原则

每条路径需要构造特定的输入，使控制流走到目标分支。选取策略：

| 路径类型 | 构造方法 |
|---|---|
| P1 / P2 | 直接传入非法参数（`None` / 负数） |
| P3–P10（税率阶梯） | 固定 `Person()` 无任何扣除，通过调整 `salary` 使 `res = salary − 5000` 落入目标税率级次 |
| P11–P18（扣除分支） | 固定 `salary = 20000`（使 `res` 落在第 3 级），逐项打开一个扣除标志 |

> 为何 P11–P18 统一用 `salary = 20000`：这样所有用例的应纳税所得额都落在**同一税率级次**，
> 使「打开某扣除项」成为唯一变量，便于定位输出差异来源。

### 期望值推导示例（WB-06）

```
输入：Person(children_num=0, is_keep_stu=0, house_loans=False,
             is_rent_house=0, supporting_elderly=False, sibling_num=0)
      salary = 20000

res = 20000 − 5000 = 15000          （无任何专项附加扣除）

税率阶梯判定：
  15000 < 0 ?      否
  15000 < 3000 ?   否
  15000 < 12000 ?  否
  15000 < 25000 ?  是 → tax = 2290 + (15000 − 12000) × 0.2
                          = 2290 + 3000 × 0.2
                          = 2290 + 600
                          = 2890
return (int) 2890 = 2890

⚠ 此处 2290 为源码常量；国标速算扣除数应为 990，正确税额 1590 元（缺陷 D1）。
```

## 3. 测试驱动程序设计

### 3.1 原始形态：硬编码 `main` 方法

实验给定源码自带的驱动：

```java
public class test {
    public static void main(String[] args) {
        Person person = new Person(2, 1, true, 0, true, 1);
        int cal = incomeTaxCalculator.cal(person, 50000);
        System.out.println(cal);
    }
}
```

**缺陷分析**：

| 问题 | 后果 |
|---|---|
| 只覆盖 1 条路径 | 17 条路径从未执行 |
| 输入硬编码 | 改动输入需改代码、重新编译 |
| **无断言** | 只打印结果，正确与否靠人眼看 |
| 无期望值 | 无法判断 9070 是对还是错 |
| 异常路径不可测 | 抛异常时 `main` 直接终止，后续用例不再执行 |
| 无报告 | 无通过/失败统计、无覆盖率 |

### 3.2 工程化形态：pytest 驱动

本项目的驱动由四部分构成：

```
tests/unit/
├── conftest.py                        # 夹具与数据驱动钩子（驱动核心）
├── test_path_coverage.py              # 18 条路径用例
└── ../data/boundary_cases.csv         # 外部用例数据
```

**（1）夹具层——把「构造被测对象」与「测试逻辑」解耦**

```python
@pytest.fixture
def sut() -> IncomeTaxCalculator:
    """被测系统：实验给定实现的忠实移植。"""
    return IncomeTaxCalculator()


@pytest.fixture
def neutral() -> Person:
    """无任何专项附加扣除的纳税人，用于隔离税率阶梯本身的行为。"""
    return Person()
```

**（2）数据驱动层——用例数据与代码分离**

```python
def pytest_generate_tests(metafunc):
    """把外部用例表参数化进测试函数。"""
    if "boundary_case" not in metafunc.fixturenames:
        return
    metafunc.parametrize("boundary_case", [...])
```

**（3）断言层——每条用例都有明确的期望值**

```python
def test_p06_third_bracket(sut, neutral):
    assert sut.cal(neutral, 20_000) == 2_890
```

**（4）报告层——pytest 内置统计 + pytest-cov 覆盖率**

```bash
python -m pytest -q --cov --cov-report=term-missing
```

### 3.3 两种驱动的能力对比

| 能力 | 原始 `main` 驱动 | pytest 驱动 |
|---|---|---|
| 用例数量 | 1 | 130 |
| 期望值校验 | ✗ 人工看输出 | ✓ 断言自动判定 |
| 异常路径 | ✗ 崩溃即中断 | ✓ `pytest.raises` 捕获 |
| 输入参数化 | ✗ 需改代码 | ✓ `parametrize` / CSV 注入 |
| 用例隔离 | ✗ 共享状态 | ✓ 夹具按用例重建 |
| 失败定位 | ✗ 无 | ✓ 精确到用例 + 实际值 vs 期望值 |
| 覆盖率度量 | ✗ 无 | ✓ 语句 + 分支 |
| 报告 | ✗ 控制台散输出 | ✓ 统计 / JUnit XML / Allure |
| CI 集成 | ✗ 需人工执行 | ✓ 退出码驱动门禁 |

## 5. 关键结论：100% 路径覆盖 ≠ 需求被满足

**这是本项目最重要的发现。**

| 事实 | 证据 |
|---|---|
| 18 条独立路径全部执行通过 | WB-01 ~ WB-18，19 passed |
| 被测方法语句覆盖率 100% | `legacy.py` Stmts 44/44 |
| 被测方法分支覆盖率 100% | `legacy.py` Branch 34/34 |
| **但计税结果错误** | 第 3~7 级每级**多计 1300 元**（缺陷 D1） |

### 为什么会漏检

白盒路径覆盖回答的问题是「**控制流有没有走到每一处**」，而不是「**每一处算得对不对**」。

```
路径覆盖能发现的缺陷：                路径覆盖发现不了的缺陷：
  · 分支条件写反（> 写成 >=）           · 常量抄错（1410 写成 110）
  · 分支遗漏（少了 else）               · 公式系数错（0.45 写成 0.4）
  · 条件冗余（永真/永假）               · 单位错（月 vs 年）
  · 不可达代码                          · 累加基数错（累进起算额错）
  · 异常路径未处理                      · 精度/取整策略错
```

缺陷 D1 属于「常量抄错」——它不改变控制流，18 条路径照样每条都走通，只是**每条路径算出的数值都偏了 1300**。因此：

> **白盒路径覆盖 + 黑盒需求验证是互补的，二者缺一不可。**

### 交叉验证

把 WB-06（`res = 15000`，白盒期望 2890）与黑盒用例
`test_bracket_boundary_values[BD-06]`（需求期望 990）放在一起看：

| 维度 | 白盒断言 | 黑盒断言 |
|---|---|---|
| 期望值来源 | 当前实现的行为 | 国标税率表 + 需求文档 |
| 期望值 | 2890 | 990 |
| 实际值 | 2890 | 2890 |
| 结论 | **通过** | **失败** |

同一条输入、同一个实际输出，在两个测试维度下得到相反结论——这正是「测试预言选择」重要性的实证。

## 6. 用例设计的局限与改进方向

| 局限 | 说明 | 改进方向 |
|---|---|---|
| 仅路径覆盖 | 不含条件组合覆盖 | 对 `is_keep_stu` × `is_rent_house` 做组合覆盖（见 [04](04-黑盒测试用例.md) 判定表） |
| 期望值来自当前实现 | 特征化断言会「锁定」缺陷 | 已用 `xfail(strict=True)` 标记需求期望，修复后自动提醒更新 |
| 单方法测试 | 未覆盖 `Person` 与计算器的交互 | 服务化后补充接口层与集成层用例（阶段 2） |
| 无异常场景组合 | 未测多参数同时非法 | 补充参数校验的组合用例 |

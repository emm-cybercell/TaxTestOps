## 2. D1 详析：税率阶梯速算扣除数少计 1300 元

### 2.1 现象

应纳税所得额 ≥ 12000 元时，**每一级都多计税恰好 1300 元**。

| 应纳税所得额 | 需求期望税额 | 实际税额 | 差额 |
|---|---|---|---|
| 11999 | 989 | 989 | 0 |
| **12000** | **990** | **2290** | **+1300** |
| 15000 | 1590 | 2890 | +1300 |
| 20000 | 2590 | 3890 | +1300 |
| 30000 | 4840 | 6140 | +1300 |
| 50000 | 10590 | 11890 | +1300 |
| 100000 | 29840 | 31140 | +1300 |

### 2.2 源码常量对照

源码采用「累进起算额 + 增量」写法：`tax = 起算额 + (res − 级起点) × 税率`。
把它换算为等价的「速算扣除数」写法（`tax = res × 税率 − 速算扣除数`）后逐级对照：

| 级次 | 应纳税所得额 | 源码起算额 | 正确起算额 | 差额 | 等效速算扣除数（源码） | 国标速算扣除数 | 差额 |
|---|---|---|---|---|---|---|---|
| 1 | `[0, 3000)` | 0 | 0 | 0 | 0 | 0 | 0 |
| 2 | `[3000, 12000)` | 90 | 90 | 0 | 210 | 210 | 0 |
| 3 | `[12000, 25000)` | **2290** | **990** | **+1300** | **110** | **1410** | **−1300** |
| 4 | `[25000, 35000)` | **4890** | **3590** | **+1300** | **1360** | **2660** | **−1300** |
| 5 | `[35000, 55000)` | **7390** | **6090** | **+1300** | **3110** | **4410** | **−1300** |
| 6 | `[55000, 80000)` | **13390** | **12090** | **+1300** | **5860** | **7160** | **−1300** |
| 7 | `[80000, +∞)` | **22140** | **20840** | **+1300** | **13860** | **15160** | **−1300** |

**注意方向**：速算扣除数**少**了 1300，等价于税额**多**了 1300。

### 2.3 正确常量的推导验证

正确的起算额由「各级距税额逐级累加」得到：

```
第 1 级：[0, 3000)       累进到 3000   = 3000 × 3%                = 90
第 2 级：[3000, 12000)   累进到 12000  = 90 + 9000 × 10%          = 990
第 3 级：[12000, 25000)  累进到 25000  = 990 + 13000 × 20%        = 3590
第 4 级：[25000, 35000)  累进到 35000  = 3590 + 10000 × 25%       = 6090
第 5 级：[35000, 55000)  累进到 55000  = 6090 + 20000 × 30%       = 12090
第 6 级：[55000, 80000)  累进到 80000  = 12090 + 25000 × 35%      = 20840
第 7 级：[80000, +∞)     最高级，由衔接条件确定 = 80000 × 45% − 20840 = 15160（速算扣除数）
```

与源码逐级比对，得到**唯一的错误点**。

### 2.4 根因定位：单一错误源，逐级传播

把源码常量序列与正确序列的**逐级增量**列出来对比：

| 增量段 | 源码增量 | 正确增量 | 是否一致 |
|---|---|---|---|
| 第 1 → 2 级 | 90 − 0 = 90 | 90 | ✓ |
| **第 2 → 3 级** | **2290 − 90 = 2200** | **900** | ✗ **多 1300** |
| 第 3 → 4 级 | 4890 − 2290 = 2600 | 2600 | ✓ |
| 第 4 → 5 级 | 7390 − 4890 = 2500 | 2500 | ✓ |
| 第 5 → 6 级 | 13390 − 7390 = 6000 | 6000 | ✓ |
| 第 6 → 7 级 | 22140 − 13390 = 8750 | 8750 | ✓ |

**结论（已确证）**：

> 全表只有**一处**增量算错——第 2 级到第 3 级的增量应为 900（9000 × 10%），源码写为 2200。
> 此后每一级的增量都正确，但因为起算额被逐级累加，**这 1300 元的错误被原样传播到全部更高级次**，
> 表现为「5 个级次各多 1300 元」。

这也解释了为什么缺陷看起来像「5 处独立笔误」，实际却是「1 个错误源」——**定位到这一点，修复范围从「逐个核对 5 个常量」缩小为「核对 1 处增量并重算后续」**。

**可能原因（推断，未证实）**：多算的 1300 元恰好等于 13000 × 10%，而 13000 是第 3 级的级距跨度。推测编码时把第 3 级的跨度误用于第 2 级的增量计算。此项为推断，源码中无注释可佐证。

### 2.5 次生现象：分界点跳变

阶梯税率函数在分界点处本应连续（收入增加 1 元，税额增加 1 × 边际税率）：

| 应纳税所得额 | 需求实现 | 当前实现 |
|---|---|---|
| 11999 | 989 | 989 |
| 12000 | 990（+1） | **2290（+1301）** |

**1301 元的跳变**是黑盒边界值测试能直接捕获该缺陷的原因。

### 2.6 影响范围

| 维度 | 影响 |
|---|---|
| 触发条件 | 应纳税所得额 ≥ 12000 元（无专项附加扣除时对应月薪 ≥ 17000 元） |
| 影响用户 | 全部应纳税所得额超过 12000 元的纳税人 |
| 单次影响 | 每人每月多缴 1300 元 |
| 年度影响 | 每人每年多缴 **15600 元** |
| 覆盖面 | 7 个税率级次中的 5 个（第 3~7 级） |
| 未受影响 | 应纳税所得额 < 12000 元（约对应月薪 17000 元以下） |

> 缺陷不在常见工资区间，这解释了为什么需求文档给出的两个样例（月薪 10000 元）都能通过——**样例测试无法发现它，只有系统性的边界值分析可以**。

### 2.7 修复建议

**不要逐个改正常量**——那样只是把「抄错」换了个位置，下次改税率还会再错一次。正确做法是**消除手抄常量**：

```python
# 反例：手抄常量，改一次错一次
elif taxable < 25_000:
    tax = 2_290 + (taxable - 12_000) * 0.2      # 2290 是错的，且无法自检

# 正例：由「级距 + 税率」推导，错误无处藏身
def build_brackets(spans_and_rates):
    """由级距与税率推导速算扣除数，杜绝手抄。"""
    brackets, cumulative, lower = [], 0.0, 0
    for upper, rate in spans_and_rates:
        if upper is not None:
            cumulative += (upper - lower) * rate
            lower = upper
        brackets.append(TaxBracket(upper, rate, round((upper or lower) * rate - cumulative)))
    return tuple(brackets)
```

该实现已在 `src/tax_service/core/policy.py` 与 `oracle.py` 中落地，并由两条用例守住：

- `test_standard_table_is_self_consistent` —— 表必须自洽；
- `test_legacy_table_is_inconsistent_in_exactly_five_brackets` —— 精确定位缺陷级次。

### 2.8 缺陷预防：从「测试发现」到「结构上不可能发生」

| 手段 | 说明 | 落地位置 |
|---|---|---|
| 数据与逻辑分离 | 税率表作为数据，计算逻辑遍历表 | `policy.py` / `oracle.py` |
| 表自洽性校验 | 速算扣除数必须等于「上界全额计税 − 累计税额」 | `test_policy.py` |
| 边界连续性校验 | 分界点处税额必须连续 | `test_defect_characterization.py` |
| 边界值用例数据化 | 边界用例放 CSV，新增级次自动扩展 | `boundary_cases.csv` |

## 3. D2 详析：住房贷款利息与住房租金同时扣除

### 3.1 现象

政策规定住房贷款利息与住房租金**不可同时享受**，但实现中两者是**两个独立的 `if`**：

```java
if (person.is_HouseLoans()) {        // 判定 ⑥
    res -= 1000;
}
// 此处没有 else / 互斥检查
if (person.getIs_RentHouse() == 1) { // 判定 ⑦
    res -= 1500;
}
```

### 3.2 验证

输入 `Person(house_loans=True, is_rent_house=1)`，`salary = 20000`：

| 场景 | 扣除额 | 应纳税所得额 | 税额 |
|---|---|---|---|
| 无住房扣除 | 0 | 15000 | 2890 |
| 仅房贷 | 1000 | 14000 | 2690 |
| 仅租金（档次 1） | 1500 | 13500 | 2590 |
| **两者同时** | **2500** | **12500** | **2390** |

税额单调下降，证明**两笔扣除都被生效**。

### 3.3 影响与修复

| 维度 | 影响 |
|---|---|
| 单次影响 | 每月多扣 2500 元专项附加扣除 |
| 性质 | 政策合规风险（可能被税务系统校验拦截） |
| 修复 | 在输入校验层增加互斥检查，拒绝同时为真的输入 |

```python
if person.house_loans and person.is_rent_house != 0:
    raise ValueError("住房贷款利息与住房租金不可同时扣除")
```

已在 `TaxOracle.validate` 中实现，由 `test_r4_loan_and_rent_are_mutually_exclusive` 与
`test_rejects_loan_combined_with_rent` 守住。

## 4. D3–D9 简析

### D3 · 兄弟姐妹数为 −1 时整数除零（🔴 严重）

```java
res -= 2000 / (person.getSibling_Num() + 1);   // sibling_Num = -1 → 除以 0
```

| 项 | 内容 |
|---|---|
| 复现 | `Person(supporting_elderly=True, sibling_num=-1)`, `salary = 20000` |
| 实际 | 抛 `ArithmeticException: / by zero`（Java）/ `ZeroDivisionError`（Python） |
| 期望 | 拒绝非法输入 |
| 影响 | **服务化后一个畸形请求即可造成 500 错误**；批量申报场景下会中断整批处理 |
| 修复 | 在参数校验层拒绝 `sibling_num < 0` |

### D4 · 继续教育 3600 元年度定额被按月扣除（🟠 中）

| 项 | 内容 |
|---|---|
| 需求 | 「取得相关证书的**当年**，按照 3600 元定额扣除」——年度语义 |
| 实现 | `res -= 3600`，作为**月度**项扣除 |
| 验证 | `Person(is_keep_stu=2)`, `salary = 20000`：实际 930 元，按年度定额应为 1590 元 |
| 全年影响 | 扣除额 3600 × 12 = **43200 元**，为政策值的 12 倍 |
| 性质 | **需求语义与函数语义错配**——既是实现缺陷，也暴露需求描述不精确（未说明年度项在月度函数中如何处理） |
| 修复建议 | 月度计算函数不应处理年度项；如需支持，应增加 `month` 参数并只在对应月份扣除 |

### D5 · 非法枚举值被静默忽略（🟠 中）

```java
if (person.getIs_KeepStu() == 1) { ... }
else if (person.getIs_KeepStu() == 2) { ... }
// is_KeepStu = 3 或 -1 时：不进入任何分支，也不报错
```

| 项 | 内容 |
|---|---|
| 验证 | `is_keep_stu ∈ {3, -1}`、`is_rent_house ∈ {4, -1}` 的输出与「无该扣除」完全相同 |
| 影响 | 调用方无法区分「传了非法值」和「确实没有这项扣除」，**脏数据被静默吞掉** |
| 修复 | 参数校验层做枚举白名单校验 |

### D6 · 赡养老人分摊额整数截断（🟡 轻）

| 项 | 内容 |
|---|---|
| 现象 | 2 名兄弟姐妹时每人分摊 `2000 ÷ 3 = 666` 元（截断），合计 1998 元，比政策少 2 元 |
| 性质 | **需求歧义**——需求未规定分摊额取整方式 |
| 需确认 | 向上取整、四舍五入，还是按赡养人约定比例？ |
| 影响 | 每人每月 2 元，规模放大后需关注 |

### D7 · 税额取整规则未定义（🟡 轻）

| 项 | 内容 |
|---|---|
| 现象 | 需求未规定取整规则，实现按 `(int)` 向零截断 |
| 验证 | 应纳税所得额 2999 元：精确税额 89.97 元，截断得 89，四舍五入应为 90 |
| 影响 | 单笔差异 < 1 元，但**批量申报与对账场景下会累积**；且不同实现（Java `(int)` / Python `int()` / 数据库 `ROUND`）结果不一致 |
| 需确认 | 取整规则须由需求方明确，并在接口契约中固定 |

### D8 · 源码注释与实现不一致（⚪ 提示）

```java
} else {   //大于80000部分税率40%     ← 注释写 40%
    tax = 22140 + (res - 80000) * 0.45;  // 实现用 45%
}
```

经核对，**国标税率为 45%，实现正确，注释错误**。属文档缺陷，但会误导后续维护者，建议修正注释。

### D9 · 冗余赋值（⚪ 提示）

```java
double tax = res;   // 该初值在所有分支中都会被覆盖，是死存储
```

不影响结果，但增加阅读负担，建议删除初值或改为声明后直接赋值。

## 5. 交叉验证：白盒与黑盒的发现能力对比

### 5.1 同一输入、两种维度、相反结论

以应纳税所得额 15000 元为例（`Person()`, `salary = 20000`）：

| 维度 | 白盒用例 | 黑盒用例 |
|---|---|---|
| 用例编号 | WB-06（路径 P6） | BD-06（边界值） |
| 期望值来源 | **当前实现的行为** | **国标税率表 + 需求文档** |
| 期望值 | 2890 | 990 |
| 实际值 | 2890 | 2890 |
| **结论** | **通过** ✓ | **失败** ✗ |

**同一条输入、同一个实际输出，在两个测试维度下得到相反结论。**

### 5.2 发现能力矩阵

| 缺陷 | 类型 | 白盒路径覆盖 | 黑盒需求验证 |
|---|---|---|---|
| D1 速算扣除数少计 1300 | 常量/数据错误 | ✗ 未发现 | ✓ 发现 |
| D2 房贷租金未互斥 | 业务规则缺失 | ✗ 未发现 | ✓ 发现 |
| D3 除零崩溃 | 边界防护缺失 | ✗ 未发现 | ✓ 发现 |
| D4 年度项按月扣 | 语义错配 | ✗ 未发现 | ✓ 发现 |
| D5 枚举值静默忽略 | 输入校验缺失 | ✗ 未发现 | ✓ 发现 |
| **5 项主要缺陷合计** | | **0 / 5** | **5 / 5** |

与此同时：

| 指标 | 白盒路径覆盖 |
|---|---|
| 独立路径覆盖 | 18 / 18 = **100%** |
| 语句覆盖率 | 44 / 44 = **100%** |
| 分支覆盖率 | 34 / 34 = **100%** |

### 5.3 结论

> **100% 的路径覆盖率，发现了 0 个缺陷；35 条黑盒用例发现了 5 个缺陷，其中包括最严重的那个。**

原因是两类方法回答的问题不同：

```
白盒路径覆盖 ──→ 「控制流有没有走到每一处？」
                  能发现：分支写反、分支遗漏、条件冗余、不可达代码、异常未处理

黑盒需求验证 ──→ 「每一处算得对不对？」
                  能发现：常量抄错、公式系数错、单位错、业务规则缺失、取整策略错
```

缺陷 D1 属于「常量抄错」——**它不改变控制流**，18 条路径每条都走通，只是每条算出的数值都偏了 1300。

### 5.4 对测试设计的指导

| 结论 | 实践含义 |
|---|---|
| 路径覆盖是**必要不充分**条件 | 覆盖率是准入门槛，不是质量结论；不可作为「测试充分」的证明 |
| 期望值必须**来源独立** | 用被测代码的行为做期望值，等于用缺陷验证缺陷（oracle problem） |
| **边界值分析**性价比最高 | D1 若只做等价类划分（取代表值）可能完全漏检 |
| 测试用例需要**双向设计** | 白盒保证覆盖，黑盒保证正确性，二者不可相互替代 |

> 的黑盒用例中**完全不可见**——只有对 Oracle 自身写用例才暴露出来。这说明：**测试代码也需要被测试**。

## 7. 缺陷处理建议

### 优先级

| 优先级 | 缺陷 | 理由 |
|---|---|---|
| P0 | D1 | 计算结果错误，影响全部中高收入纳税人，合规风险 |
| P0 | D3 | 进程崩溃，服务化后可直接被畸形请求触发 |
| P1 | D2 | 政策合规风险，可能被税务校验拦截 |
| P1 | D4 | 年度/月度语义错配，需与需求方确认后统一口径 |
| P2 | D5 | 输入校验缺失，影响数据质量与问题定位 |
| P3 | D6, D7 | 需求歧义，需需求方明确规则 |
| P4 | D8, D9 | 可维护性，随手修正 |

### 修复后的回归验证

修复 D1 后，以下用例状态会发生变化，需同步处理：

| 用例 | 当前状态 | 修复后状态 | 处理动作 |
|---|---|---|---|
| BD-06 ~ BD-14（9 条） | xfail | **XPASS → 失败** | 移除 xfail 标记 |
| WB-06 ~ WB-18（11 条） | 通过（特征化断言） | **失败** | 更新为需求期望值 |
| `test_d1_*`（4 条） | 通过 | **失败** | 删除特征化断言 |
| `test_legacy_table_is_inconsistent_*` | 通过 | **失败** | 更新为「表已自洽」 |

> **这正是 `xfail(strict=True)` 与特征化测试的价值**：修复不会「静默通过」，而是强制更新用例，
> 确保测试集始终反映真实行为。
